01 / FIELD NOTES

Install

One line. It downloads the signed release, verifies the signature and the checksum, runs the full test suite — and then stops.

# read it first — it is served as plain text on purpose
curl -fsSL https://talos-agent.ch/install.sh | less

# then run it
curl -fsSL https://talos-agent.ch/install.sh | bash

Or from source, if you would rather see everything:

git clone https://github.com/talos-kernel/talos.git
cd talos
python3 -m venv .venv && . .venv/bin/activate
pip install --require-hashes -r requirements.lock -r requirements-dev.lock
python -m pytest tests/ -q
The installer starts nothing

It proves the build and hands you back your shell. Nothing starts listening until you say so. Review the configuration before you start an agent that can use a shell.

Python 3.11 or newer, Linux or macOS. The shell tool needs bubblewrap on Linux; macOS uses the built-in sandbox-exec. Where there is no isolation, the shell refuses rather than running unprotected.

02 / FIELD NOTES

Give it an identity

The configuration starts with an empty identity allowlist. Telegram needs an explicit operator identity; the local terminal has a bootstrap rule described below. The setup wizard records your channel-qualified identity.

Start in your terminal with two guided steps: confirm your local identity, then choose your model connection. No Telegram account is needed.

python -m talos setup terminal
python -m talos chat

For a Telegram bot, run python -m talos setup, then python -m talos. The wizard prints the file it writes and the next command. It preserves other settings, stores the detected CLI path, and saves each section atomically with mode 0600. The key that matters:

TALOS_ALLOWED_PRINCIPALS=telegram:123456789,cli:1000

For live tool tracking, set TALOS_STATUS_STYLE=expressive. One activity card updates in place while the answer stays separate. Answers retain their formatting after approval buttons; tables become compact labelled rows. Long runs maintain one short update, edited every 60 seconds with completed actions, failures and the current activity. Completion, cancellation and approval waits stop these updates. Private tool arguments and hidden reasoning are never included. One editable milestone explanation can appear before the next tool call and become the final answer. After result delivery, temporary work messages are removed; the result and execution log stay. Approval prompts show the exact command, and stored approvals apply only to the action you approved.

An identity is channel-qualified. The same number on a different channel is a different identity — so a Telegram account that may command Talos grants nothing to an email address spelling the same name.

The command line is a channel like any other. On a fresh install — allowlist still empty — the local caller is admitted as cli:<uid> automatically, so the first run works. The moment the list names one identity it becomes exhaustive: add a Telegram account and your uid must appear as cli:<uid> too, or talos chat and talos ask fall silent. A shell next to the agent is not an argument for granting it something.

The config file is the boundary

talos.env carries the bot token, the API keys and the allowlist. It is Tier A in the kernel's own floor: reading is refused, writing needs a human. Otherwise the kernel would stay intact while the list of who may command it came from a file the agent could rewrite.

On a real deployment, hand it to another user entirely — root:agent, mode 640, directory owned by root too. doctor treats that as the better state, not a finding.

03 / FIELD NOTES

Give it a mind

Talos does not ship a model. It talks to one — through an API key, or through a CLI you already have installed and logged in.

python -m talos models              # the catalogue
python -m talos models --refresh    # ask the providers directly
python -m talos setup model
Provider recovery in the current source build

A model limit does not block service startup or /model, /status, /queue and /stop. Status distinguishes model availability from service operation. An explicit model switch validates before saving. A declared empty response may retry the same model call once within its original time budget; tools and jobs are never replayed. The provider does not change automatically. Queue notices follow the actual turn state. An interrupted foreground request remains in active conversation context with an explicit unfinished status, so a short follow-up keeps its subject without replaying completed tools.

Find and understand a setting before changing it:

python -m talos config list model
python -m talos config describe TALOS_STATUS_STYLE
python -m talos config set TALOS_STATUS_STYLE expressive
python -m talos config validate
python -m talos help setup

config works on the selected file; process environment variables can override it. Restart a running service after changing file settings. For a different Claude executable, rerun setup model or set TALOS_CLAUDE_BIN in the protected configuration.

Each provider carries its own key and its own base url, resolved at the moment of the call:

ANTHROPIC_API_KEY=sk-ant-…
OPENAI_API_KEY=sk-…
Why one key per provider, and not one key

Until 2026-08-05 a single value served every provider, so selecting an OpenAI-shaped route sent an Anthropic key to OpenAI as a bearer token. Tests with identical placeholder keys cannot see that bug. Switching to a provider whose key is missing now fails the switch — the previous provider stays active instead of a conversation dying mid-turn.

05 / FIELD NOTES

The terminal session

START A TERMINAL SESSION
python -m talos chat

The session header identifies the active model, your channel-qualified identity and whether terminal approval is available. Check that context before asking the agent to act.

Approvals hang on the terminal

When the kernel needs a person to answer, whether one is there is measured: both stdin and stdout must be a real terminal.

How you started itWhat happens when a human is needed
talos chatA person is there — you are asked, and you answer with the next line.
talos chat < jobs.txtNo terminal → refused, with the reason stated.
talos chat > out.logNobody would read the question → refused.
talos ask "…"Always refused. A one-liner waits for nothing.

Answering is just typing: yes, no, or always — the last creates a standing rule for that exact action, bound to its arguments, never to the tool's name.

A session cannot start itself

The agent has a shell. If it could run talos chat inside it, it would be giving itself orders with no channel and no reader. Both chat and ask refuse when they detect the agent's own sandbox around them.

06 / FIELD NOTES

Work on the side

Some questions take two minutes, and the conversation should not stand still for them.

› /background go through /var/log and summarise today's errors

Background #1 started: go through /var/log and summarise today's…
  id bg_a1b2c3d4e5f6 · runs unattended, so anything needing approval is refused

The result arrives later as its own message, marked as a report rather than as a reply to whatever you asked in the meantime.

A background task is a scheduled run, not a helper with your rights

Nobody is sitting in front of it. So the same ceiling applies as for a timed run: anything that would need a human becomes a refusal. A question dropped into a chat where another conversation is running is the most reliable way to get a “yes” on the wrong thing.

Its context is empty — it gets the task and nothing else. Two runs sharing one history write into each other, and afterwards nobody can say which of them said what. The result does not go back into the history either.

At most three run at once. Each one costs a thread, tokens and model time; without a cap a dozen typed tasks leave you with a machine that has stopped answering.

07 / FIELD NOTES

What it remembers

The conversation is kept per channel, in memory only, and it is bounded twice — by turns and by characters. An unbounded history is an unbounded prompt (cost, latency, drift) and an unbounded leak: what was said three weeks ago would go out to the model again today.

When the bound is reached, the middle is summarised and the ends are kept verbatim. The head usually carries the actual task; the tail carries whatever “and that too” refers to.

You:                  set up the backup for the NAS
Agent:                done — see /etc/backup.d
Earlier (summarised): discussed retention, settled on 30 days; the
                      NFS mount needed the hard option
You:                  and add the offsite copy
A summary is labelled as one

It is never disguised as a verbatim turn. A summary that looks like something actually said is a claim about words nobody used — and the model could quote it back as if it were.

If summarising fails, the oldest turns are dropped as before. The bound is not a comfort feature: a history that kept growing after a failed summary would turn a cost question into a leak.

/new clears the active context, summary included. The event log and the searchable archive stay — “forgotten” here means precisely: out of the prompt.

Skills it writes for itself

Longest-lived memory of all: a skill on disk is read into every prompt from the next turn on. So the one write path into the skills directory, skill_write, is declared irreversible — the kernel answers NEEDS_HUMAN without exception, and an unattended run gets a DENY. It creates only: never overwrites (atomically, not by looking first), never writes allowed-tools, never anything that looks like a credential, never outside the skills root. Improving a skill means the operator deletes it first. The weekly skill-distillation blueprint (“every sunday 20:15”) turns the week's event log into at most one candidate and takes exactly this path — or parks the candidate as a vault note when nobody is there to approve.

In-session commands

The same set in the terminal and in the messenger — one command centre, not two. There is deliberately no separate vocabulary for the CLI.

CommandWhat it does
/helpWhat this installation understands. Add a word to filter commands, such as /help background.
/policy <path|cmd>What the kernel would decide — without doing it.
/btw <task> · /bg · /backgroundRun an independent background task. Its labelled result returns here; the main conversation stays separate.
/tasksYour running background jobs, with IDs.
/steer <instruction>Correct the main task at its next step. Add a bg_id to correct a background job.
/cancel <bg_id>Stop one background job at its next step; the foreground continues.
/queue <task> · /qTelegram: queue a separate next task. Without text, show the queue.
/whoamiYour identity, chat and access, without a model call.
/approve taskAllow every approval-required action until this task ends or is stopped. No clock expiry. Hard kernel denials remain.
/approvals · /approve alwaysInspect the pending decision or save an exact-action standing rule.
/autonomy [0-5]Show or tighten the dial. It can only ever narrow what the kernel allows.
/undoReverse the last write, from the snapshot the executor took.
/newClear the active context, summary included.
/logThe recent events, in the chat.
/revoke <n>Drop a standing approval, by its number from /allowed.
/stopEnd the running task, its task consent and task-related pending decision. No consent carries into a new task.
/stopallStop everything stoppable: thought, queue, background tasks, pending approvals — discarded, never approved. Timed runs stay.

Every verdict the kernel can return:

Allow

It runs, and the receipt says what it touched.

Needs human

You are asked — with the kernel's facts, not the model's description of itself.

Deny

No path forward except a different request.

10 / FIELD NOTES

When something won't work

Start with the doctor. It reads, counts and looks — it creates no directory, writes no file, starts no service, and shows no secret.

python -m talos doctor

Every finding carries its remedy in its own text, because the agent reads these lines too: a finding without a remedy becomes “it isn't set up”, which is right and useless.

capabilities
  ok   grab_frame (ffmpeg)   /usr/bin/ffmpeg
  ·    web_search (ddgs)     missing — `pip install ddgs`, no key needed

Why did it refuse that?

talos events --tool run_shell     # find the id
talos why 4831                    # the verdict, the rule, and what followed

why names the rule that applied and the targets it applied to — and says out loud that those targets were derived from the real arguments, never taken from what the model wrote. Then it shows the rest of the same run, because “refused, and then?” is the question that makes people stop reading logs.

What should this installation change?

talos review

It reads its own log and reports patterns worth acting on: the same wall hit repeatedly, approval prompts worn out by repetition, proposals the kernel refuses every time, and capabilities that are missing and have actually cost runs. It also runs by itself after a turn, at most once a day, and says nothing when there is nothing to say.

Proposals only

The review never applies anything and has no function that could. A standing rule created out of “you approved this three times” would be a second source of permission built from the agent's own history — the exact thing capability tokens exist to prevent.

11 / FIELD NOTES

Channels

Every way in fetches. Telegram long-polls; mail pulls over IMAP. Nothing listens on a port, because a webhook would turn an outbound-only process into a reachable one.

WhatsApp has two implementations of one channel name. The Cloud-API variant stays delivery-only: Meta's inbound path is a webhook, and a webhook is exactly the port this design refuses to open. The broker variant receives without one. A listener on an operator-controlled WhatsApp broker reachable over SSH appends the messages routed to Talos to a JSONL queue. Talos pulls that queue over SSH with a persisted byte cursor: first run at end-of-file, cursor never advanced by a failed poll. Replies go back through the broker's send script. The sender number comes out of the operator's own WhatsApp account, so this variant carries Trust.FULL — conversations live in the same whatsapp:<number> namespace either way. Off by default: TALOS_WA_BROKER_SSH (the SSH target), TALOS_WA_BROKER_QUEUE, TALOS_WA_BROKER_CLI_DIR. Configured, the broker wins over the Cloud API — the registry demands unique names, and this is the one that fetches.

ChannelTrustNotes
telegramFULLButtons for approvals, live status, images in.
cliFULLchat and ask. Approvals only at a terminal.
mailASKSender proven from the receiving server's Authentication-Results, fail-closed.
whatsappFULL · NOTIFYBroker over SSH pull (FULL) — or Cloud API, outbound only (NOTIFY).
A From: header is not an identity

It is chosen by the sender and IMAP verifies nothing, so an allowlist keyed on it is bypassed by one line of text. Talos trusts only an Authentication-Results header stamped by the TALOS_MAIL_AUTHSERV_ID it is configured to expect — and without that configuration the sender stays unproven, fail-closed.

12 / BOUNDARIES

Understand the boundaries

Talos is an alpha project. The permission kernel checks declared tool calls; isolation and the worker protocol define what delegated code can do inside a job.

  • One permission path. New interfaces must use the existing dispatcher and identity checks.
  • A plan is not approval. Every step still passes the kernel with its actual arguments.
  • Worker network access exists. Filesystem confinement does not imply a network firewall or a verdict on every inner MCP action.
  • The Computer is experimental. Its first backend targets ARM64 Linux with KVM. A macOS, Windows or x86 Computer backend is not implemented.
  • Configured authority matters. The agent can still act within the permissions its operator grants. The kernel is not a guarantee against every mistake.

Read the limits of the test evidence and the worker boundaries before expanding access.

13 / FIELD NOTES

Let Codex take a scoped coding task

Enable the worker on both sides. The agent needs its existing worker switch and socket, plus TALOS_CODEX_BACKEND=1. The worker needs an installed Codex CLI and an authenticated, private credential home:

TALOS_CLAUDE_WORKER_CODEX_BIN=/usr/bin/codex
TALOS_CLAUDE_WORKER_CODEX_HOME=/var/lib/talos/codex-home

Authenticate as the worker user. Protect the directory with mode 0700 and its auth file with 0600. Each job gets an auth-only copy in its disposable workspace. Missing configuration fails before the job starts. MCP and browser tasks remain on the Claude backend.

The CLI runs inside Talos's mandatory outer sandbox. A completed worker turn still needs the appropriate file or test check before you call the task finished. Read the full worker setup and boundaries →

14 / FIELD NOTES

Start with something you can check.

After configuring your model and chat identity, try these in your own conversation. No sample needs a secret, an external message or a production change.

  1. Read: ask Talos to read a README in its workspace and explain how the project starts.
  2. Make: ask for a small notes file inside the workspace. Read it back and use /undo to verify recovery.
  3. Inspect: use /log to see the recorded calls, or /stop to interrupt a running thought.

For an enabled coding worker, describe the task, the relevant source material and a testable result. Wait for the job's terminal receipt, then inspect its artifacts.

15 / OPTIONAL · EXPERIMENTAL · SEPARATE PROVISIONING

Your own Computer

A persistent Linux workspace for terminal commands, scripts, jobs and project files. Headless is the default; a desktop is optional. The browser-based workbench remains available in either mode.

The initial backend needs ARM64 Debian Linux, KVM, systemd, two guest CPUs and a 40 GB virtual disk. Allow 2 GB guest RAM for headless mode, or 4 GB with a desktop. Provisioning is separate from the ordinary Talos installer.

talos computer setup

That command describes provisioning in a source build with Computer support. The experimental Computer is included in 0.19.1-alpha; provisioning remains a separate step. Read the complete Computer guide for the actual setup commands, required privileges and boundaries.

computer_run always receives a kernel decision for its exact arguments. Approval is the default; an operator may explicitly enable attended auto-approval in protected configuration. computer_status reads receipts, files and routine templates. Stable operation keys prevent an interrupted write from being silently replayed. A zero exit code remains marked for review unless the requested file checksum checks pass.

Use /computer in the bound operator's private chat to open the workbench. Pause and stop are available in either mode. Semantic browser actions can inspect, fill and submit forms headlessly, with bounded response receipts. With the optional desktop, takeover cancels active guest actions before enabling the mouse and keyboard. During takeover, the optional on-screen Keyboard offers mobile typing, text entry and shortcuts. It clears unsent text when control ends. Expand, Fullscreen and 100–200% zoom make the computer easier to see.

One operator, one VM

Projects share the computer. Private HTTPS and a personal access link protect the workbench. This is a separately provisioned environment, not an anonymous public desktop.
